## 0. The question, made precise

The ask: for **T3 content**, can the Wolfram **local/cloud MCP** connection be
used; can the **Wolfram Demonstrations** corpus, via MCP, become a source of
customised content; and what is the right strategy given Wolfram is a quality
standard.

**"T3" disambiguated (repo audit).** Four tier vocabularies exist; two matter
here and both put Wolfram at tier 3 by convention:
- `src/verification/tiered-orchestrator.ts` — answer-verification **Tier 3 =
  Wolfram|Alpha arbitration** (built-in slot; `registerVerifier()` reserves
  tiers ≥4 for extensions).
- `src/content/resolver.ts:297` — the content resolver's own `tier3()` =
  "Wolfram MCP verification for high-stakes", calling the same
  `verifyProblemWithWolfram`.

So "T3 content" = **content whose mathematical truth is anchored by a CAS**,
with Wolfram as the reference standard. That is this strategy's scope.

## 2. Premises (final gate confirms)

1. **Rendered widgets stay dependency-free (hard rule); budgeted synchronous
   verification calls are the existing pattern (already live in the cascade).**
   The line is drawn precisely: no student page ever *renders* through
   Wolfram (embeds, iframes, live plots — rejected); the cascade's occasional
   capped verification call inside a grade request is today's architecture and
   stays.
2. **The standard is already encoded — the switch is off, and the switch has a
   license question in front of it.** Activation is ~15 operator minutes of
   code-free work, but the ToS read comes FIRST (Premise 5).
3. **SymPy carries the bulk; Wolfram arbitrates the residue.** The repo's own
   documented architecture ("RAG → SymPy → Wolfram") is the right one and was
   simply never built. A free, local, license-clean CAS does the
   high-volume **authoring-time and CI-time** checking (B1d: never in
   production /api paths — the live cascade stays RAG → LLM → Wolfram);
   Wolfram's quota and licensing exposure shrink to arbitration of what
   SymPy can't parse or disagrees on. This plan builds the missing layer —
   including the three vaporware prerequisites under it — instead of routing
   around it.
4. **Demonstrations are a design standard, not a content library — and
   curation is parked, not scheduled.** NC + dead CDF close the import path.
   The idea-level standard is real but is backlog material (TODOS), not a
   committed deliverable with metrics: its legal gate is unlikely to clear
   soon and it does not serve the pilot.
5. **No licensing fact in this plan is settled, so nothing license-bearing
   activates before the terms are read.** Commercial API $/call, LLM Kit
   price, Engine production license, Show Steps redistribution, and whether
   "pre-revenue pilot" even qualifies as non-commercial — all unconfirmed.
   The operator's terms-pull GATES production activation, not just future
   monetized use.
6. **MCP is an authoring instrument, and W-B is BLOCKED (not merely
   "unlocked") by connector authorization.** A session that finds the Wolfram
   MCP unauthenticated must stop and report — never proceed, never
   approximate a CAS result.

## 3. The strategy — two moves, one posture, one parking lot

### Move A — Activate the standard, license-first (operator, ordered, ~1 hour)
1. **A1 (gates A3):** pull the terms: WA API commercial pricing + whether the
   pilot qualifies for the free tier's non-commercial clause; LLM Kit price;
   Engine production-license terms; Show Steps redistribution terms. Record
   verbatim in a NEW top-level section of
   `docs/ops/content-verification-runbook.md` — "§0. Licensing terms (gates
   Tier 3 activation)" placed before the existing §1 (the runbook is
   currently pilot-mechanics-only; the operator needs a named home, not
   "somewhere in this file"). (All four pages are
   proxy-blocked from agent sessions — this is genuinely operator work.)
2. **A2:** authorize the **Wolfram MCP connector** for Claude sessions
   (claude.ai Settings → Connectors → Wolfram). Unlocks the W-B posture.
3. **A3 (only after A1 clears it):** obtain the AppID and set
   `WOLFRAM_APP_ID` on the Render service. Tier 3 verification, gate-ledger
   `wolfram_verified` evidence, `wolfram-verify-job`, and the pilot's
   `wolframCheck` leg go live — zero new code, 50-calls/day cap already
   enforced.

### Move B — Build the missing CAS layer + provenance honesty (code, eng-review-shaped)

The eng review found the SymPy story sits on THREE stacked pieces of vaporware,
so B1 is restructured into prerequisites-first sub-items (each a finding, each
now scoped):

1. **B1a — the AnswerVerifier contract infrastructure (prerequisite, was
   vaporware).** `runAnswerVerifierContract` exists only in prose
   (`types.ts:15` docstring + EXTENDING.md's tutorial, whose step 3 imports a
   module that does not exist; EXTENDING.md's file tree lists FOUR
   nonexistent files). Build `src/verification/verifiers/contract.ts`
   mirroring `src/content/verifiers/contract.ts`'s working shape, plus
   `example.ts`'s `AlwaysTrueVerifier`, and fix EXTENDING.md's file-tree +
   tutorial so it is literally followable — a **named acceptance criterion**,
   not a side effect.
2. **B1b — make Tier-4+ verifiers actually execute (was: never invoked).**
   `TieredVerificationOrchestrator.verify()` never reads `extraVerifiers` —
   the registry is populate-only, so ANY registered verifier is dead code
   today. Add the invocation loop + a test that a registered mock verifier's
   `.verify()` fires end-to-end (the current registry test asserts only
   registration semantics). **Placement decision, resolved per premise 3:**
   SymPy is NOT a Tier-4 extension — satisfying "SymPy before metered
   Wolfram" means a hardcoded stage between Tier 2 and Tier 3 (a "tier 2.5"
   named stage), keeping `registerVerifier()`'s ≥4 slot reserved for checks
   that genuinely run after Wolfram. `tierUsed` gains an additive value
   (`tier25_sympy` or similar); any CHECK constraint / consumer of the
   closed enum is enumerated lockstep (the ErrorTag-extension pattern).
3. **B1c — the SymPy verifier itself.** Local `sympy`, sandboxed subprocess,
   Solve/simplify/equality for closed-form GATE material. Refusal spec (D8):
   `reason` names the unparseable head verbatim (e.g.
   `sympy: could not parse head 'Piecewise'`), `agrees:false, confidence:0`,
   never a guess; subprocess timeout returns a refusal, never throws (the
   `verify()` doc contract).
4. **B1d — deployment shape, decided: authoring/CI-time only.** Neither
   Docker image has python3; CI runners have python3 but not sympy. Chosen
   shape: SymPy runs in authoring sessions and CI (one `pip install sympy`
   step added to the workflow) — **never** in production `/api` paths; the
   Dockerfiles are untouched and a documented decision states
   `/api/scoring/grade` must not depend on SymPy presence. Premise 3 is
   scoped accordingly: *SymPy carries the bulk of authoring-time and CI-time
   checking*; the live cascade stays RAG → LLM → Wolfram.
5. **B2 — provenance convention, collision-aware.** The suffix convention
   (`…+sympy` / `…+wolfram` + `verified_at`) is enforced in
   `check-practice-items.ts` **scoped to items carrying `generation_run_id`
   provenance** (the established E8 boundary — the 505 committed free-text
   items are untouched, no new baseline file). The factory's locked
   `PracticeItemVerificationPath` enum values (`dual_model_consensus`,
   `wolfram_verified`) are grandfathered as always-valid bare forms — a
   regression test locks both branches so the pilot's first promoted items
   cannot fail the gate (the eng review's 2a collision).
6. **B3 — `/verify-sweep` full rewrite** (repoint undersold it): every
   section of the skill doc describes behavior the real `wolfram-verify-job`
   doesn't have. Rewrite against the real job — bundle-file scope, checkpoint
   flow, and the actual env caps (`WOLFRAM_RATE_MS`, `WOLFRAM_MAX_CALLS_PER_RUN`,
   `WOLFRAM_STEPS_MAX_PER_RUN`) — delete phantom tables, and add a
   doc-matches-code grep test (the `check-ci-aggregate-drift` pattern).
7. **B4 — evidence surfacing: already satisfied, five-minute confirm.**
   `ReviewQueuePanel.tsx` already renders per-gate `reason` under "Gate
   evidence" — B4 is a QA confirmation with one synthetic item, not open
   work.

### Posture W — Wolfram MCP in authoring sessions (no build, blocked on A2)
In MCP-authorized sessions, agents use `WolframLanguageEvaluator` **ad hoc**:
CAS-check answer keys that SymPy refused or that arbitration needs; prototype
plots to sanity-check a gif-scene or widget spec before committing it;
sanity-check parametrized problem families. Rules — with the enforcement mechanics named: the harness usually injects a
pre-emptive "requires authentication" notice for unauthenticated MCP servers;
when it does not, the FIRST tool call's auth error is itself the stop signal —
on either signal the session stops, never retries, never approximates a CAS
result, and reports in BOTH places: the user-facing response and a TODOS.md
entry naming the blocked work. Results recorded per B2's convention; no dedicated
WL→widget translation adapter is built until repeated real sessions
demonstrate the need (the adapter idea is recorded in TODOS with its trigger:
"3+ authoring sessions each hand-translating WL output").

### Parking lot (TODOS.md, not this plan's scope or metrics)
- **Demonstrations-as-visual-standard curation** (`concept → demo idea →
  widget spec` mappings) — parked with its trigger: a real legal read on
  independent re-implementation + the pilot complete. MIT preview snapshots
  usable as authoring reference if/when picked up.
- **WL→safe-evaluator translation adapter** — trigger above.
- **Show Steps content in worked examples** — trigger: A1's terms answer.
- **Wolfram Engine batch asset generation** — trigger: a demonstrated need
  `gifenc` can't meet AND a production license.

### Rejected (explicit)
- **R1 — student-facing Wolfram Cloud embeds/renders**: uptime dependency
  with a documented outage history; violates the dependency-free widget rule;
  free-tier 60-day expiry rots pages silently.
- **R2 — importing/embedding Demonstrations content**: CC BY-NC-SA; CDF dead.
- **R3 — MCP inside the generation pipeline**: duplicates the cascade's
  post-hoc verification, adds latency and a live dependency to every
  generation call.

## 5. Failure modes

| Path | Failure | Handling |
|---|---|---|
| A1 terms say free tier doesn't cover the pilot | A3 waits for a paid key decision; SymPy (B1) carries verification meanwhile — the plan degrades to license-clean | by construction |
| Tier 3 live, key invalid/quota hit | cascade falls back (confidence-penalized LLM verdict), never blocks | existing, tested |
| SymPy can't parse an expression | honest refusal naming the head; item routes to Wolfram arbitration or hand-check — never guessed | B1 spec |
| SymPy and Wolfram disagree | item flagged to the review queue with both values; writer guard already refuses silent overwrites | existing D5 + B2 |
| MCP session finds connector unauthenticated | stop on the harness notice OR the first auth error; report to user + TODOS — never approximate | posture rule (mechanics in W) |
| Production image lacks python/sympy | non-issue by design: B1d confines SymPy to authoring/CI; /api paths never depend on it (documented decision + test) | B1d |
| Pilot items hit the B2 vocabulary gate | cannot happen: bare factory enum values grandfathered, gate scoped to generation_run_id provenance, both branches regression-tested | B2 |
| Demonstrations legal read negative (if ever picked up) | parked item stays parked; independent-code specs unaffected | parking-lot trigger |

## 6. Success metrics
1. A3: production logs show Tier 3 active; first `wolfram_verified` evidence
   rows in the gate ledger.
2. B1: contract infra real (EXTENDING.md tutorial followable end-to-end);
   Tier-4+ invocation wired with an execution test; SymPy stage green in CI;
   authoring-time checks show SymPy carrying the bulk with Wolfram reserved
   for arbitration (observable in `verification_log.tier_used` once the
   additive stage value lands).
3. B2: `ci:practice-items` enforces the provenance vocabulary; zero items
   claim CAS verification without a structured record.
4. Pilot service: operator minutes-per-verified-item with CAS evidence
   attached vs without (the review queue's meter already measures it).

  operator's).
