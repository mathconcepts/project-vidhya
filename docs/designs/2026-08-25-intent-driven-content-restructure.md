## 1. The problem, restated honestly

Demo review verdict: **"content is not addressing a definite problem statement."**

The root cause is structural, not editorial. Vidhya's content is organized
**supply-side**: concept → pedagogical stages (intuition → discovery →
formalism → worked example → practice). That is the right spine for a mastery
engine. But a student never arrives at a page thinking "I would like an
intuition stage." They arrive with a job:

- *"Eigenvalues GATE CS PYQs and practice questions"* → give me real questions, now
- *"Which test do I use for this series?"* → help me pick a method
- *"What are the transpose properties?"* → give me the exact property, fast
- *"I've never seen Laplace transforms"* → teach me from zero

The uploaded intent research makes this concrete: **203 atomic sub-topics**,
each profiled with the representative query, the intent class, the pain point
that costs marks, and the format students expect. The intent distribution is
the headline finding:

| Intent (what the student came to do) | Atoms | Share |
|---|---|---|
| PYQ discovery / targeted practice | 98 | 48% |
| Guided problem solving / method selection | 70 | 34% |
| Concept clarification / property recall | 18 | 9% |
| Foundation learning | 17 | 8% |

**Only 8% of demand is "teach me from zero" — yet the current lesson
structure opens every concept in teach-from-zero order.** 82% of demand is
practice and method selection. The content is not wrong; it is answering a
question most students didn't ask. That is exactly what "not addressing a
definite problem statement" feels like in a demo.

**An honesty caveat this plan is built around (outside-voice finding, accepted):**
the catalogue is *structured research*, not measured demand. Its 203 rows
derive from query templates (each module's rows share one templated pain
point, expectation, and format), so the intent distribution above is a
hypothesis about demand, not analytics. It is also *searcher* intent, while
the demo critique concerns the in-product experience. Consequences threaded
through this plan: (a) the catalogue intent decides the default lane only for
cold arrivals — for a signed-in student with state, the readiness engine's
recommendation wins; (b) the distribution gets validated against real
behavior (aggregate, surveillance-invariant-compatible counters) before any
irreversible routing decisions; (c) inventory targets are planning constants,
not demand-derived quotas.

### Premise challenge (0A)

1. **Is this the right problem?** Yes, with a sharpening: the fix is not
   "more content" or "better content" — it is making every sub-topic page open
   with a **definite problem statement** (the pain point + the exam intent +
   the marks at stake) and routing the student into the lane matching their
   intent. Content volume is a Phase-4 consequence, not the fix itself.
2. **Proxy skepticism.** The research workbook carries SEO fields and
   competitor benchmarks. Those are acquisition instruments, not the
   objective. The objective stays what the platform already measures:
   **holdout PYQ accuracy delta and mastery lift**. SEO fields are committed
   as data but nothing in this plan optimizes for them at the expense of the
   learning loop.
3. **What if we did nothing?** The demo keeps failing the same review. The
   mastery engine (Elo, FSRS, FIRe, readiness arms) is real and working, but
   invisible — because the front door doesn't name the problem it solves.
   This is a packaging failure burying an engineering success.

### The out-of-the-box insight

The demand-side research and the supply-side engine **already rhyme** — nobody
had joined them:

| Catalogue intent (demand) | Readiness engine arm (supply, `src/readiness/next-best-action.ts`) |
|---|---|
| Foundation learning | **Teach** |
| PYQ discovery / targeted practice | **Practice** |
| Concept clarification / property recall | **Retain** |
| Guided problem solving / method selection | **Diagnose** |

The four intents students express in search are the four arms the readiness
engine already schedules. The restructure is therefore **a joining layer, not
a rebuild**: intent picks the lane on arrival; the readiness engine picks the
lane when the student asks "what next". Same vocabulary, two directions.

## 2. Implementation alternatives (0C-bis)

**APPROACH A: Page-level re-skin (minimal viable)**
- Summary: keep everything as is; add an intent-tab UI over existing concept pages; write problem-statement blurbs by hand.
- Effort: S | Risk: Low

- Cons: intent is cosmetic — nothing routes, measures, or generates against it; 203 hand-written blurbs drift; the question-inventory gap (126 vs 8,725) stays invisible; next demo review finds the same hollowness one click deeper.
- Reuses: concept pages, AtomCardRenderer.

**APPROACH B: Demand-side sidecar layer (ideal architecture) — RECOMMENDED**
- Summary: commit the catalogue as a versioned data layer (`data/curriculum/gate-em/`) with a locked intent-profiles contract; map atoms onto the existing concept spine (`concept_ids`, many-to-many); drive page framing, lane routing, blueprint templates, question-inventory CI floors, and trap-drill generation from it. Mastery stays keyed on `concept_id`; demand stays keyed on `atomic_id`.
- Effort: M (phased) | Risk: Medium
- Pros: one source of truth for intent; every downstream system (blueprints, floor gates, generation runs, readiness routing) reads the same file; the 8,725-question target becomes a measurable CI-tracked floor; extends cleanly to 8 GATE papers; no disruption to Elo/FSRS/FIRe keys.
- Cons: two taxonomies to keep mapped (atom ↔ concept); mapping is editorial work (26 of 203 done in this PR); needs a validation gate so the mapping can't silently rot.
- Reuses: blueprint StageKind/AtomKind vocabulary, readiness arms, holdout PYQ machinery, error-tag pipeline, batch generation, syllabus-floor gate pattern.

**APPROACH C: Replace the concept graph with the 203-atom taxonomy**
- Summary: make atomic_id the primary key everywhere; regenerate the concept graph from the catalogue.
- Effort: XL | Risk: High
- Pros: single taxonomy; page = mastery unit.
- Cons: invalidates every Elo rating, FSRS card, FIRe edge, and holdout mapping keyed on concept_id; the catalogue's granularity is optimized for search demand, not for mastery modeling (AT-001..003 are one mastery unit but three search queries); throws away 47 hand-justified `encompasses:` edges.

**RECOMMENDATION: B.** It is the only approach where intent becomes
load-bearing (routing, generation, measurement) rather than paint, without
destroying the mastery engine's keys. Maps to the engineering preferences:
engineered-enough, explicit over clever, right-sized diff.

## 4. Vision (EXPANSION mode)

### 10x check
The 10x version is not "better lesson pages." It is **"the portal that knows
why you came."** Engineering Mathematics is the one section shared by every
GATE paper — 13–15 marks for CS, ME, EE, CE, EC, IN, DA, XE alike. The
catalogue's `papers` field makes Vidhya the first tool that treats EM as a
cross-paper product: eight landing pathways ("Engineering Math for GATE CS:
the 13 marks you can lock in"), one mastery engine underneath. Competitors
(Unacademy, Made Easy, PW, GO Classes) sell full-paper courses; nobody owns
the shared section with adaptive practice. That is the wedge.

### Platonic ideal
A student searches "rank nullity GATE questions" at 11pm, three weeks out.
The page opens: *"GATE asks rank–nullity as a 1-mark property check — and
students lose it to row-operation slips, not theory. 12 PYQs across CS/EE/ME.
You: unrated. 25 minutes to your first clean run."* One tap: the PYQ ladder
starts, calibrated by warmup. A wrong answer doesn't say "incorrect" — it
says *"sign flip in row 2, the #1 trap on this sub-topic"* and schedules a
trap drill. The next morning, the retain arm resurfaces the property card.
The student never saw "intuition stage"; the student felt *seen*.

### Delight opportunities (≥5, each ~30-min scale with CC)
1. **90-second win**: every sub-topic's practice lane opens with one real PYQ the student can beat in 90 seconds after the lesson — before/after proof of progress.
2. **Intent switcher chips**: "I'm here to: Learn / Look up / Solve / Practice" — remembered per student per module.
3. **"Where marks die" heatmap**: per module, the named error tags aggregated from cohort error logs, shown on the module landing page.
4. **Property cards as FSRS cards**: every `clarify`-lane property card is schedulable by the retain arm — look-ups convert to long-term memory automatically.
5. **Trap drill of the day**: one drill generated from the student's own dominant error tag, framed by the module's pain profile.
6. **Method-picker decision trees**: the `solve` lane's first interaction is "answer 2 questions about the problem's shape → the tree names the method" — the catalogue says 70 sub-topics need exactly this.
7. **Paper-aware chips**: each atom shows which of the student's papers it applies to (`papers` field) — a CS aspirant never wastes a session on an XE-only sub-topic.

## 5. The redefined content structure (the deliverable)

Every one of the 203 sub-topics resolves to an **Intent-Resolved Learning
Unit**. This is the contract, versioned in `data/curriculum/gate-em/`:

```
AtomicUnit (AT-xxx)  ──  one searchable student problem
│
├── PROBLEM STATEMENT (definite, rendered first, always)
│     pain point (module profile) + exam intent + marks at stake
│     + time budget + the student's own state (unrated / rated)
│
├── INTENT LANES (all four exist; atom's declared intent = default lane;
│   lanes map 1:1 to readiness arms)
│   ├── learn    → intuition → discovery → formalism → worked ex. → practice   [Teach]
│   ├── clarify  → property card → counterexample → PYQ anchor                 [Retain]
│   ├── solve    → decision tree → worked example → graded practice            [Diagnose]
│   └── practice → PYQ anchor → drill ladder (mix per inventory plan)          [Practice]
│
├── PAIN-POINT TRAPS
│     named error tags (module profile) → trap drills → error_log wiring
│
├── QUESTION INVENTORY (CI-gated floor)
│     target_total (35/40/45) split MCQ/MSQ/NAT/PYQ-variant,
│     difficulty 30/50/20 foundation/standard/stretch
│
├── PREREQUISITES   requires → AT-graph (+ concept_ids → mastery spine)
│
└── MEASUREMENT     concept-keyed mastery, holdout PYQ delta, lift experiments
```

Machine-readable form:
- `data/curriculum/gate-em/atomic-catalogue.json` — all 203 atoms (intents, pain points, formats, inventory targets, prerequisite graph, LA concept mapping).
- `data/curriculum/gate-em/intent-profiles.yml` — the four lanes' stage sequences in blueprint vocabulary + eight module pain profiles with error-tag mappings.

Routing rule (locked, outside-voice finding 5 accepted): **catalogue intent
is the cold-arrival default; student state wins.** An anonymous or unrated
visitor landing on an atom gets the atom's declared lane. A signed-in student
with mastery state gets the readiness engine's arm; the lane chips remain one
tap away. The lane↔arm table in §1 is a shared *vocabulary*, not a routing
identity — a property look-up (clarify) is not an overdue review (retain),
and the router never pretends it is.

Progressive lanes (outside-voice finding 6 accepted): a lane chip renders
only when its content exists. "Every page serves all four lanes" is the
contract's end state, not a launch gate — an atom with only a PYQ ladder
shows one chip, honestly, rather than three hollow ones. Full lane build-out
is ~600–800 authored artifacts across the catalogue; it rolls out per module
under the same floor-gate discipline as questions.

Measurement grain (outside-voice finding 8 acknowledged): mastery, lift and
holdout deltas are **concept-keyed**, and several atoms share one concept
(calculus 39→19, prob-stat 36→8). Atom-level lift claims are out of reach at
current grain; `experiment_assignments` already supports `target_kind='atom'`
for assignment, but the mastery snapshot cell stays the concept. Phase 3
experiments are therefore scoped to concept-level lift, stated as such.

Three deliberate contract choices:
1. **Two keys, one mapping.** `concept_id` remains the mastery key (Elo, FSRS, FIRe, holdout untouched). `atomic_id` is the demand key (pages, search, SEO, inventory). `concept_ids[]` joins them, many-to-many. An unmapped atom means "mapping not yet done", never "no concept".
2. **No new runtime enums.** Lanes are expressed in the existing `StageKind`/`AtomKind` vocabulary; `property_card` and `decision_tree` are `presentation` hints on existing kinds, so the blueprint validator, orchestrator and renderer need extension, not surgery.
3. **No learner state in content data.** The workbook's per-learner columns were dropped at commit time (surveillance invariants 1–10 hold).

## 7. Phased implementation

**Phase 1 — Commit the contract (this PR).** Catalogue + intent profiles +
README + this design doc. Data only; zero runtime change; zero risk.

**Phase 2 — Problem-statement layer (next PR).** Two hard dependencies land
FIRST (outside-voice finding 3 accepted):
1. **PYQ → atom mapping.** `pyq-bank.json` carries no concept/atom mapping
   today — the `ci:la-walkthrough` test leg is red for all 26 LA concepts for
   exactly this reason. 48% of atoms default to the practice lane, whose
   first stage is a PYQ anchor; without the mapping the flagship lane opens
   empty. Mapping LA's PYQs is the Phase 2 gating task, and it is the same
   work the walkthrough gate is already waiting on.
2. **Catalogue validation gate** (see T3) so the data can never drift ahead
   of its checks again.
Then: render the DPS block + intent-lane chips on mapped LA atoms.
`problem_statement_frame` placeholders (`{pyq_count}`, `{marks}`,
`{time_budget}`) are **derived at render time** from the PYQ mapping and
marking data — any placeholder without a real value renders an honest reduced
frame, never a fabricated number. Feature-flagged (`VIDHYA_INTENT_LANES=on`),
default off until QA.

**Phase 3 — Blueprint intent templates.** `template-engine.ts` reads the
atom's intent and emits the lane's stage sequence; new additive rationale
codes (`intent_pyq_practice`, `intent_method_selection`, `intent_property_recall`,
`intent_foundation`). Lift ledger groups by rationale — the existing groupby
answers "does intent-aware sequencing move mastery?"

**Phase 4 — Inventory floors + generation.** Extend the floor gate to read
`question_inventory` targets per atom; report-only first (the honest 126 vs
8,725 gap), then ratchet per module as batch generation runs fill it.
Feasibility stated plainly (outside-voice finding 4 accepted): the gap is
~8,600 items and **verification, not generation, is the bottleneck** — the
123 existing LA items were answer-key-verified by hand against a second
method plus Wolfram. Scaling requires the tiered verification cascade plus
deterministic marking gates plus a sampled hand-verification protocol (rate
TBD from the first module's error rate), and live provider keys exist only in
operator environments. Every run launches with a dry-run cost estimate and an
experiment wrapper (existing behavior). The 45/40/35 targets are planning
constants — the ratchet per module is set by measured PYQ frequency and
verification throughput, not by the workbook's numbers.

**Phase 5 — Trap drills + error-tag extension.** Migration extending the
`ErrorTag` union CHECK (031) with the proposed tags in `intent-profiles.yml`;
misconception-miner briefs per module profile; trap-drill generation targeted
at dominant error tags.

**Phase 6 — Cross-paper pathways.** Eight paper landing pathways via
`exam_packs` rows + `papers` filtering. Discrete Mathematics and the
remaining module mappings land here (they are CS/DA-paper content beyond the
current gate-ma spine). Two identity questions to settle at Phase 6 design
time (outside-voice finding 11): how one student's concept-keyed Elo/FSRS
state spans per-paper packs (recommendation: packs filter the shared spine;
state never forks), and the `interactives_enabled=false` default for
operator packs vs the foundation lane's `manipulable` stage (the lane
degrades to `visual_analogy` where interactives are gated off).

**Mapping ownership (outside-voice finding 10 accepted):** the atom→concept
mapping is the plan's central join and cannot stay "editorial work, someday".
Quota: each phase that touches a module maps that module completely before
its UI lands (Phase 2 = LA done here; Phase 4 first generation module ships
mapped; Phase 6 completes the rest). CI reports mapped-atom count so the 177
unmapped atoms are a visible burn-down, not a footnote. Where the spine is
too coarse (prob-stat: 8 concepts for 36 atoms), extending `concepts:` in
`gate-ma.yml` is part of that module's mapping task — the spine grows
deliberately, atoms never map to concepts that don't deserve to exist.

## 8. Architecture (Section 1)

```

              ┌───────────────────────────┐    ┌────────────────────────────┐

              └────────────┬──────────────┘    └──────────▲─────────────────┘
                           │  concept_ids[] (many-to-many)│
                           ▼                              │
              ┌───────────────────────────┐               │
              │ intent-profiles.yml        │               │
              │  4 lanes → stage sequences │               │
              │  8 pain profiles → tags    │               │
              └────────────┬──────────────┘               │
             ┌─────────────┼───────────────┬──────────────┤
             ▼             ▼               ▼              ▼
      ┌───────────┐ ┌──────────────┐ ┌───────────┐ ┌──────────────┐
      │ DPS block │ │ blueprint     │ │ inventory │ │ readiness    │
      │ + lane    │ │ intent        │ │ CI floor  │ │ arms ↔ lanes │
      │ router UI │ │ templates     │ │ + batch   │ │ (join only)  │
      └───────────┘ └──────────────┘ │ generation│ └──────────────┘
                                     └───────────┘
```

Data flow, four paths (catalogue → page render):
- **Happy**: atom mapped → DPS block + default lane rendered.
- **Nil** (atom has no `concept_ids`): page renders the existing concept view unchanged; no DPS block; log at debug. Never a broken page.
- **Empty** (catalogue file missing/unparseable at build): build fails loudly (validation script), never a silently intent-less deploy.
- **Error** (intent value outside the four known): validation gate rejects at CI; runtime treats as nil-path.

Coupling: frontend and blueprint engine gain a read-only dependency on the
catalogue (build-time constant, like `concept-graph.ts` already is). No new
runtime service, no new DB table in Phases 1–4. Rollback = feature flag off
(Phase 2+) or git revert (Phase 1); no migration to unwind before Phase 5.
