# Buyer Q&A: Demo Prep for Admin / Principal Review

Generated by `/plan-ceo-review` on 2026-08-19. Branch: `claude/ceo-review-demo-prep-7hepzw`.

Audience: a school admin or principal evaluating Vidhya. They are not engineers.
Each question below gets three things:

1. **The ELI5 answer** you can say out loud, word for word.
2. **Show, don't tell** — the exact screen to open while you say it.
3. **Receipts** — the code and CI facts backing the claim, so you never
   promise something the product doesn't do.

Where the honest answer is "not yet", the gap is named here and a scoped
change plan for it lives in the "Required changes" section at the end.
Never bluff a principal. "Here's what it does today, here's what ships next
month" closes deals; a caught bluff ends them.

The 3-minute guided demo path is `docs/moat-demo.md`. This doc is the Q&A
layer on top of it.

## Q1. Knowledge graph: how are you sure you're taking the RIGHT subject content?

**ELI5 answer (speak this):**

> "We don't let the AI guess the syllabus. We start from the official exam
> syllabus and write it down as a machine-readable map: about a hundred
> concepts for GATE Mathematics, with arrows saying what you must know
> before what. Then a robot checks the map on every single change we make:
> every concept must have a real explanation, an interactive, at least five
> practice problems that actually grade, and at least one real past exam
> question mapped to it. If any concept is missing any of those, the build
> fails and nothing ships. And the final proof isn't our opinion: we keep a
> locked set of real past exam questions the system is never allowed to
> teach from, and we measure whether students get better at those. Real
> exam questions are the ground truth, not our content."

**Show, don't tell:**
- `/knowledge-home` — the FrontierSpine view: the concept map with
  prerequisite arrows, mastered rollups, "You are here".
- `/admin/holdout` — the locked past-question bank with its stratification
  by year and topic, and the accuracy timeline.

**Receipts:**
- Syllabus source of truth: `data/curriculum/gate-ma.yml` and
  `data/curriculum/jee-main.yml`, hand-authored against the official
  syllabi. The 97-concept graph in `src/constants/concept-graph.ts` is
  regenerated at build time, so client and server can never drift.
- Coverage is mechanical, not aspirational: `npm run ci:la-walkthrough`
  (`scripts/check-la-walkthrough.ts`) checks all four legs (explanation,
  interactive, 5+ gradable practice items, mapped PYQ) for every
  linear-algebra concept, derived from the graph, and blocks CI. All four
  legs are green for all 26 LA concepts as of v4.35.0 (PR #107).
- Answer keys for the LA floor were recomputed by hand via a second method
  and spot-checked against Wolfram before the gate went live (v4.34.0).
- Ground truth: the holdout PYQ bank (migration `024_pyq_holdout.sql`),
  ~30 PYQs per exam stratified by (year, topic), deterministically seeded,
  with a locked invariant that a question never moves between practice and
  holdout. Teaching units declare which PYQs they prepare for
  (`curriculum_units.prepared_for_pyq_ids`), and lift is measured against
  holdout accuracy (`computePyqAccuracyDelta`).
- Quality gate on new content: the Tier 4 PedagogyVerifier scores every
  generated unit on a 5-criterion rubric where concept fidelity is the
  heaviest weight (0.30).

**Honest gap:** the four-leg walkthrough gate is enforced for Linear
Algebra (26 concepts) today; the other GATE-MA topics have the syllabus
floor gate but not yet the full four-leg guarantee. Say "Linear Algebra is
our proven-depth vertical; the same gate extends topic by topic."

## Q2. When a student makes mistakes, how do you strengthen fundamentals? How is the knowledge graph used?

**ELI5 answer:**

> "Every wrong answer gets a tag for WHY it was wrong: sign slip, wrong
> method, misread the question. The concept map knows what depends on
> what. So when a student keeps failing eigenvalues, the system doesn't
> just drill eigenvalues harder. It checks the concepts underneath, like
> determinants and linear systems, and if those are shaky it walks the
> student back one step first. There's literally a 'Diagnose' mode inside
> the engine that picks the next action: sometimes the best next action is
> not more practice, it's finding the real gap. And it works in both
> directions: getting an advanced question wrong quietly lowers the
> system's confidence in the basics it builds on, so those basics come
> back for review sooner. The AI tutor sees the same picture: when it
> explains something, it's told which prerequisites this student is shaky
> on, so the explanation fills the actual hole."

**Show, don't tell:**
- `/attempt/:id` — answer a question wrong, show the graded result.
- `/knowledge-home` — point at the prerequisite arrows while explaining
  the walk-back.
- The tutor (`/chat`): ask a question about an advanced concept with a
  persona that has weak prerequisites.

**Receipts:**
- Error tags persist per attempt (`attempt_error_tags`, migration 031)
  with a locked tag vocabulary; `mock-to-marks` separates "didn't know it"
  (method errors) from "knew it but slipped" (careless tags).
- The readiness engine's four arms are Retain / Practice / Teach /
  Diagnose (`src/readiness/next-best-action.ts`);
  `SyllabusAwareReadinessEngine` filters candidate concepts by
  prerequisite mastery over the DAG (`eligibleNodes`).
- Downward propagation: FIRe (`src/gbrain/fire.ts`) applies a bounded
  penalty to encompassed fundamentals when an advanced attempt fails, and
  implicit credit when it succeeds, over 47 hand-justified `encompasses:`
  edges (flag `VIDHYA_FIRE=on`).
- Scheduling: FSRS-6 memory model brings weak material back at the right
  time; overdue cards with low recall outrank fresh practice by design
  (extraction-first tie-breaking in the readiness engine).
- Tutor context: `src/personalization/student-context.ts` threads
  `shaky_prerequisites` and `recent_misconceptions` into the LLM prompt,
  built on demand and never persisted.

## Q3. How does content stay updated, and how does MY custom content (PDFs) feed the right personalization?

**ELI5 answer:**

> "Two loops keep content fresh. A generation loop creates new problems
> and lessons every night where gaps exist. A measurement loop scores
> everything that exists: content that measurably helps students gets
> promoted to canonical, content that measurably hurts gets pulled,
> automatically, every night. And once a week the whole system re-verifies
> its own answer keys to catch drift. For your own material: upload a PDF,
> we read the text out of it, tag it to the concept it covers, and from
> then on the student's lessons and tutor can pull from YOUR material when
> that concept comes up, clearly labelled as coming from your upload. Your
> documents stay private: they never enter analytics, never go to outside
> AI services without explicit consent per request, and they're deleted
> when the account closes."

**Show, don't tell:**
- `/uploads` — upload a born-digital PDF live, show the extraction.
- Then ask the tutor or open a lesson on the tagged concept, and point at
  the "From your private uploads" disclosure line.
- `/admin/content-rd` — the effectiveness ledger with lift per experiment,
  and the promote/demote status badges.

**Receipts:**
- Freshness loops: trend collection → priority scoring → content flywheel
  → feedback scoring (`src/jobs/`), plus the nightly learnings ledger
  (`src/jobs/learnings-ledger.ts`) that promotes winners
  (lift > 0.05, p < 0.05, n ≥ 30) and demotes losers so
  `applyMediaUrls` stops serving them. Weekly `/verify-sweep` re-verifies
  generated problems and demotes failures.
- Uploads: `src/content/uploads.ts` (born-digital PDF text extraction via
  pdf-parse, 10 MB cap), routed by `src/content/router.ts` (a dedicated
  `find-in-uploads` intent, plus automatic surfacing alongside any lesson
  whose concept matches a tagged upload).
- Privacy guarantees are written as code comments labelled
  "constitutional": no cohort telemetry, no external API calls without
  per-request consent, hard-delete on account close.

**Honest gaps:**
- Scanned / photographed PDFs are refused honestly ("couldn't read this
  PDF, scanned docs not yet supported") rather than mangled. Math OCR is
  parked deliberately.
- Uploads personalize RETRIEVAL (what gets shown) today, not GENERATION
  (the problem generator does not yet mint new problems out of your PDF).
  Say it exactly that way if pressed; the generation hookup is a scoped
  roadmap item.

## Q4. Bidirectional traceability (Subject ↔ Practice), optimized by user intent?

**ELI5 answer:**

> "Both directions are literal database columns, not a diagram on a
> slide. Every teaching unit lists the real exam questions it prepares
> you for. Every one of those exam questions points back at the unit that
> teaches it. Every practice problem carries the ID of the generation run
> that created it, so we can trace any question on screen back to the
> exact configuration, cost, and experiment that produced it. And a robot
> checks the round trip for every concept: explanation, interactive,
> practice, and past exam question must all connect, or the release is
> blocked. On intent: when a student asks for something, a classifier
> first decides what they actually want, revision, a fresh explanation,
> something from their own uploads, and routes to different content for
> each. The same student asking the same question in different modes gets
> different, appropriate material."

**Show, don't tell:**
- `/admin/holdout` — per-PYQ rows showing `taught_by_unit_id`.
- Pick any LA concept in `/knowledge-home` and walk all four legs:
  lesson → interactive → practice → its mapped PYQ.

**Receipts:**
- Bidirectional links: `curriculum_units.prepared_for_pyq_ids` ↔
  `pyq_questions.taught_by_unit_id` (migrations 023/024), maintained
  transactionally by the unit orchestrator.
- Provenance: `generation_run_id` columns on `generated_problems`,
  `atom_versions`, `media_artifacts` (migration 020).
- The round trip is CI-enforced per concept by `ci:la-walkthrough`;
  v4.35.0 mapped every LA question to every concept it tests (with
  `also_tests` cross-references reported as secondary coverage).
- Intent: `src/content/intent-classifier.ts` (6 intents) feeding
  `src/content/router.ts`; per-session stance pinning
  (`src/sessions/stance-pin.ts`); and the 5-layer personalization
  re-ranker (`src/personalization/selector.ts`: syllabus 0.10, exam 0.05,
  cohort 0.30, mastery 0.30, error 0.15, realtime 0.10) applied inside
  lesson composition.

## Q5. Time-pressed, anxious, last-minute students: enabler, not guardrails?

**ELI5 answer:**

> "Nothing in the student experience is locked. There are no forced
> paths: a student three weeks from the exam can open any lesson, any
> practice set, any mock, anytime. What changes is the ADVICE. The engine
> knows how many weeks remain and shifts its recommendations through
> phases: early on it favors learning new ground, in crunch time it
> favors retention and marks recovery. For anxious students specifically,
> the system reorders how material is presented, worked examples and
> visual intuition first, raw practice last, because a wrong answer at
> the wrong moment spikes anxiety. And the highest-leverage last-minute
> tool is the marks-recovery report: after any mock we split every lost
> mark into 'didn't know it' versus 'knew it but slipped'. Slips, sign
> errors, misreads, are the cheapest marks to win back in the final week,
> and we tell the student exactly which drill recovers the most."

**Show, don't tell:**
- `/warmup` — the 5-item placement: an anxious late joiner is placed in
  about five questions instead of starting from a fake zero.
- The NextBestActionCard on the planned session page, with its phase
  label ("Crunch time — ...").
- `/admin/scenarios` — the side-by-side neutral vs. personalized render
  for the anxious persona (priya-cbse-12-anxious). This is the proof
  personalization is real, not theatre.

**Receipts:**
- Phase awareness: `src/readiness/syllabus-context.ts` (`inferPhase`:
  early / mid / crunch / final-week, with per-phase arm weights); the
  phase label lands in the recommendation rationale.
- Anxiety handling: `MotivationAwareTeachingPolicy`
  (`src/teaching/motivation-aware-policy.ts`) with a locked modality
  table; anxious students get practice last, deliberately.
- Marks recovery: `src/readiness/mock-to-marks.ts` (`summarizeMock`:
  earned / knewIt / leftOnTable / lossByErrorType /
  topDrillRecommendation).
- The admin journey timeline is explicitly "never gates navigation"
  (PR #58), and milestones/nudges apply to operators, not students.

**Honest nuance (only if pressed):** checkpoint quizzes carry one pacing
rule, a study-time threshold and a content-depth check before a quiz
unlocks, enforced server-side. Frame it as "quiz readiness": quizzing you
on material you haven't touched produces noise, not signal. Everything
else, practice, lessons, mocks, the tutor, is open at all times.

## Q6. Wolfram and interactive content: how is content dynamic, not static?

**ELI5 answer:**

> "Wolfram's job is referee, not author. Every generated math problem
> passes a three-step check: first a cache of already-verified patterns,
> then two AI models must independently solve it and agree, then Wolfram
> Alpha checks the final answer symbolically. The AI never gets to grade
> its own homework on the number. The dynamic part comes from three
> built-in things. One: live applets, no plugins, where the student drags
> a slider and the math re-evaluates in real time, so one applet is
> effectively infinite worked examples with different numbers. Two: a
> generator that mints fresh problems, new numbers, new variations, for
> any concept-difficulty-error combination that runs thin, each verified
> before a student ever sees it. Three: explanations themselves are
> personalized at request time, the AI is told this student's
> representation preference, mastery, and shaky prerequisites, so two
> students asking about the same concept get different explanations."

**Show, don't tell:**
- A `manipulable` interactive in an LA lesson: drag the slider, watch the
  derived value re-evaluate live.
- A `simulation` atom (parametric animation) and a `guided_walkthrough`
  (prompt → hint → answer per step).
- `/admin/content-rd` → RunLauncher: show the dry-run cost estimate for
  generating a fresh batch, proof generation is a live capability, not a
  frozen bank.

**Receipts:**
- Verification: `src/verification/tiered-orchestrator.ts` (RAG cache →
  dual-solve consensus → `src/verification/verifiers/wolfram.ts`); the
  same cascade backs descriptive grading, where "the CAS is the source of
  truth on the number, the LLM never decides correctness"
  (`src/scoring/rubric-grader.ts`).
- Interactives: `Manipulable.tsx`, `Simulation.tsx`,
  `GuidedWalkthrough.tsx` under
  `frontend/src/components/lesson/interactives/`, driven by a safe
  formula evaluator (recursive-descent parser, provably no `eval()`,
  tested). Parametric GIF scenes render server-side from `gif-scene`
  blocks.
- Generation: `/content-gap` fills (concept × difficulty × error-type)
  holes via the adaptive generator; per-student quizzes are assembled
  live from due reviews + frontier concepts (`src/readiness/quiz-pool.ts`)
  with a 14-day no-repeat window.
- Personalized explanations: `student-context.ts` payload
  (representation_mode, mastery, misconceptions, shaky prerequisites)
  threaded into the prompt.

**Honest gap:** there is no one-click "same question, try with different
numbers" re-roll on a specific problem yet. The generator mints fresh
variants at the pool level, not per-problem on demand. Scoped as change
C3 below.

## Q7. Mock practice: full-length, topic-wise, random time "for a feel"?

**ELI5 answer (current — C1/C2 shipped):**

> "Full-length mocks are live: timed, built to the exam's real section
> weights, tuned to the student's current level, graded entirely on the
> server with real GATE negative marking, and the answer key never
> reaches the browser until submission. You can now also scope a mock to
> one or more topics, say, Linear Algebra only, and the question count
> and duration rescale to match. And you can choose how the clock feels:
> Standard is the full duration, Compressed trims 5-15% off (a different,
> reproducible amount each time), Rush is a flat 30% off for real
> exam-day pressure. On top of that, short concept-scoped checkpoint
> quizzes, six questions, exam-paced at 80 seconds a question, drawn from
> what that student is due to review."

**Show, don't tell:**
- `/mock-exam` — pick a topic or two from the chip row, pick Rush timing,
  start the mock, and show the timer bar naming the mode; after submit,
  the by-topic breakdown, the marks-recovery report, and the "you did
  this under rush timing" line.
- A checkpoint quiz from the XP meter, showing timer auto-submit.

**Receipts:**
- Full-length: `generateMockExam()` samples PYQ + verified generated
  problems by section weights and mastery-shifted difficulty; migration
  047 binds exams to their owner (IDOR fixed), grading is server-side,
  submission is idempotent, and `GET .../mock-exam/:sessionId` strips the
  answer key.
- Topic-wise (C1): `generateMockExam()`'s `selectedTopicWeights()` filters
  and renormalizes `MARKS_WEIGHTS` over the requested topics;
  `GET .../mock-exam/:sessionId?topics=linear-algebra,calculus` validates
  against the same canonical topic set and 400s a typo by name.
  `GET .../mock-exam/topics` gives the frontend picker that exact
  id/label set — deliberately not `GET /api/topics`, which uses a
  different id namespace (`transforms`/`discrete` instead of
  `transform-theory`/`discrete-mathematics`, and is missing two topics
  outright).
- Exam-feel timing (C2): `timingModeMultiplier()` is a pure function of
  the exam id — `rush` is a fixed 0.7×, `compressed` a deterministic
  0.85-0.95× seeded from the id (never `Math.random`, so a reload or a
  grading replay always agrees with the timer the student watched).
  Migration 049 persists the chosen mode on the `mock_exams` row.
- Verified against a real local Postgres (not just mocks): after seeding,
  a Linear-Algebra-only mock draws its full 65-question quota from real
  `generated_problems` rows; Rush yields a 126-minute exam (180 × 0.7)
  exactly as computed.
- Quizzes: `src/api/quiz-routes.ts` + `src/scoring/xp.ts`
  (QUIZ_LENGTH=6, 80s/item), graded through the same deterministic GATE
  scorer and student-model path as all practice.
- Timer correctness: `TimerPrimitive.tsx` runs two registers so expiry
  auto-submits what was actually answered (stale-closure bug fixed).

**Honest gap:** C3 (per-problem "try with new numbers" re-roll) is still
open — see below.

### C2. Exam-feel timer modes (including "random time") — SHIPPED

- `timingModeMultiplier(examId, mode)` — pure function: `rush` = fixed
  0.7×, `compressed` = a deterministic 0.85-0.95× seeded from the exam id
  (no `Math.random` — a reload or grading replay always agrees with the
  timer the student watched), `standard` = 1.0× (unchanged default).
  Applied to `time_limit_minutes` once, at exam creation.
- Migration `049_mock_exam_timing_mode.sql` — `mock_exams.timing_mode`,
  persisted at creation, entered into
  `scripts/schema-column-baseline.json` with rationale (config choice,
  never aggregated).
- `?mode=standard|compressed|rush` on the generate request, validated;
  surfaced in the generate response, the in-progress timer bar, and the
  post-submit report ("you did this under rush timing"), reading back
  from the stored row so a replayed double-submit still reports the
  original mode.
- Tests mirror C1's — pure-function bounds/determinism, route validation
  + persistence + replay, frontend chip selection + query param + results
  copy.

**Verified against a real database, not just mocks:** this session had no
live Postgres attached, so it started the repo's own native `postgresql`
service (no Docker daemon available in the sandbox — `docker-compose.yml`
assumes one), ran `autoMigrate()` through migration 049, seeded both PYQ
and Linear-Algebra practice-item content, and called `generateMockExam()`
directly. A Linear-Algebra-only mock drew its full 65-question quota
from real DB rows; Rush produced a 126-minute exam (180 × 0.7) exactly as
predicted; a two-topic Compressed mock landed at 162 minutes (0.9× of
180, within the promised 153-171 range).

### D1. Linear Algebra content now backs the database, not just files — SHIPPED

Closing a gap C1 exposed: all 26 LA concepts already had authored,
verified practice items (`data/practice-items/gate-ma-la-*.json`, 130
items — the v4.34 "content floor" work), but they lived ONLY as
disk-backed content served through `FileLearningObjectCatalog` for
ordinary practice. `generateMockExam()` queries the `generated_problems`
Postgres table directly via SQL — so before this change, a
Linear-Algebra-scoped mock exam had zero real DB rows to draw from
despite the content existing.

- `src/db/seed-la-practice-items.ts` — `seedPracticeItemsFromDisk(pool)`,
  mirroring the existing `seed-static-pyqs.ts` boot-seed convention
  exactly (idempotent, a DB-unreachable run degrades and resumes next
  boot rather than crashing it). Each item's stable JSON id hashes to a
  deterministic UUID, so this is a genuine UPSERT: editing an item's
  text in the source JSON re-syncs the same row next boot, and running
  it twice never duplicates.
- Wired into `src/server.ts`'s boot sequence, right after the existing
  static-PYQ seed — runs on every boot, same as migrations.
- Verified live: 130/130 items upserted into `generated_problems` across
  all 26 canonical LA concept ids (confirmed via direct SQL against a
  real local Postgres, not just a mocked pool in tests).
- `src/db/__tests__/seed-la-practice-items.test.ts` — 9 tests against the
  real JSON fixtures: full count, every one of the 26 concepts present,
  correct topic slug (not the file's display-cased label), verified
  flag, deterministic id shape, genuine upsert (`ON CONFLICT DO UPDATE`),
  and idempotency across two runs.

### C3. "Same question, new numbers" re-roll — P2, still open

Per-problem dynamic variants, the concrete thing a principal means by
"this cannot be fully static". Reuse two existing pieces: the adaptive
generator (generate a variant scoped to the same concept, difficulty,
and question kind as the source problem) and the tiered verifier (the
variant is served only after it verifies). Ship as a "Try with new
numbers" button on `PracticeAttemptPage` that requests a verified sibling
from the pool first (instant) and falls back to live generation when the
pool is thin. The pool-first path makes the demo reliable even with no
provider key.

Effort: human ~3 days / CC ~2 hours.

### C4. Scanned-PDF math OCR — P3, parked deliberately

Keep the honest refusal. Do not promise OCR in the demo; the register
(§5.6) parks it because silently mangled math is worse than refusal.
