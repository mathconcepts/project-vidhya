## Problem (CEO statement)

Verbatim intent: interested people wanted a sample full-features walkthrough of one topic (e.g. Linear Algebra). Currently only static content is displayed — interactives are generated but not rendered. Prepare a demo plan for a full-functionality walkthrough "for a feel." Audiences: students whose confidence is low, and a skeptical principal. Think out of the box: the walkthrough can display multiple combinations of user journeys highlighting the powers of Project Vidhya. The visitors shall come out resonating with Vidhya's capabilities.

## Premise findings (Step 0)

- **The ask is two problems wearing one coat.** (1) An engineering wiring gap: interactive atoms are generated (interactive-spec v1: manipulable / simulation / guided_walkthrough; MathBox 3D + MathBoxLite SVG fallback; enrichment blocks) but LessonPage renders static content — the rendering framework and `InteractiveLessonBlock.tsx` exist, the generated interactive atoms are not wired into that path, and MathBox loads three.js from a CDN (dies on floor devices/offline venues). (2) A demo experience design: persona-shaped journeys, because a low-confidence student and a skeptical principal need opposite emotional architectures.
- **The principal is E3-lane, and this is the named decision.** Zero-to-Many parks institutes "until inbound pull, as a named decision." A principal requesting a demo IS inbound pull. This plan records the named decision, scoped strictly to serving this demo: no institute onboarding, no pricing talk, no E3 build. The principal is logged in the SSOT People tab with the E3 tag per the standing rule.
- **The pre-call build ceiling is spent; this plan records the owner override.** The Three Rooms plan made further pre-call build contingent on a recorded owner override. This demo serves expressed demand from real interested people — the same demo-enablement class the Aug-5 pack legitimized. The override is recorded here, named, like D5/D7 before it. Its boundary: only work serving the walkthrough for these expressed-interest visitors; anything else waits.
- **The demo sessions ARE conversations — with counting criteria, so the gate isn't diluted.** A student demo session counts toward the 8-conversation gate only when it meets the gate's intent: ≥15-20 minutes observed (a 5-minute rail walk alone does not count), run under the observation call script, with Observations fields captured same-day (verbatim quotes, stall point, surprise). This plan does not compete with the assignment — executed correctly, it advances it.
- **Honest demo law (restated before temptation arrives):** demo mode never fakes. Fixture profiles carry visible sample-data chips (settled demo-theater discipline); wins are earned on real items; a rigged "correct!" or an invented number would hand a skeptical principal exactly the lie he is scanning for. The receipt aesthetic is the demo's spine, not its casualty.

## Accepted scope (this plan)

**M1 — Make it true (the A-milestone; the demo floor):**
0. **Step 0: code-confirm the load-bearing claims (½ day, before the rest of M1 is committed).** This plan was written corpus-grounded, no repo clone. Before building: confirm the exact seam between generated interactive atoms and the enrichment path, confirm generated specs match interactive-spec v1's current shape (else the H1 shim enters scope), confirm the MathBox CDN dependency as documented, and confirm the Aug-5 `--compare` preview plumbing exists in the shape D3.1's split-screen assumes. Output: a go/re-estimate checkpoint — if the seam differs from the docs, M1 is re-estimated BEFORE it proceeds, not discovered mid-build.
1. **Interactive rendering wiring.** Generated interactive atoms (interactive-spec v1 kinds) render on LessonPage and `/admin/preview` through the existing enrichment → `InteractiveLessonBlock` path. Unrenderable or version-mismatched specs degrade to the atom's static representation with a logged counter — never a blank block, never a crash (error map below).
2. **MathBox local bundling.** three.js + mathbox move from unpkg CDN to the build (or the venue-safe equivalent: vendored assets served same-origin). `MathBoxLite` SVG fallback stays as the floor-device path. Budget check: the 3D path lazy-loads only on capable devices, decided by a runtime capability probe (WebGL context creation + `navigator.deviceMemory` where present) checked against the standing P-class budget table — feature detection, not user-agent guessing.
3. **Linear Algebra fill.** `content:sample-pack` run scoped to the LA chapter exemplars: every atom type, every enrichment block kind, L3 interactives where the registry covers (eigen/vector/matrix-transform concepts first — they demo best). Snapshot fixture (Aug-5 D8) extended to cover the LA exemplars so demo concepts are CI-protected from run-induced regressions (this extension is pre-authorized to slip to M2 if the M1 clock tightens — the pack output itself is verified by eye for the demo either way).
4. **Walkthrough scripts v1.** One per audience (student / principal), written for Giri-narrated screen-share — the insurance demo that exists from M1 day one. Authorship split, stated: CC drafts scripts and all caption copy; Giri reviews every line against the no-puffery rule before anything is shown to a visitor.

**M2 — Make it walkable:**
5. **`/demo` entry + fixture-profile seeder.** Demo mode behind `DEMO_MODE_ENABLED` (false on the production instance; true only on the local venue instance — see Locked decisions). Personas: low-confidence aspirant, near-topper, teacher, principal. Each persona = a seeded fixture profile (diagnostic taken, mastery vector, error history, speed profile shaped to make its journey coherent). Fixture data is internally consistent all the way down: aggregates reconcile to per-student rows reconcile to attempts (D3.2's coherence requirement, enforced by a validator — tests below). Sample-data chip on every fixture-backed surface, always.
6. **Journey card deck (D3.6).** `/demo` home renders 5-6 cards (persona × scenario): "3 weeks to GATE, weak in LA" · "just failed a mock" · "topper pushing rank" · "teacher checking batch coverage" · "principal auditing outcomes" · (slot for one more from observed demand). A card = fixture profile + entry route + rail ordering, in `config/demo-rails.json`, validated at build. Every shipped card is QA-walked end to end; a card that dead-ends is pulled, not shipped.
7. **Demo isolation.** Fixture profiles live in demo-namespaced storage, seeded PER DEVICE SESSION: two visitors on two devices walk independent fixture instances simultaneously (the vision's principal-and-student-at-the-same-table case), and the reset button is per-device, resetting only that device's instance. Demo attempts never write to real STUDENT-DATA tables, real ledgers, or the resonance pipeline (a `demo` provenance flag at the storage boundary, asserted by test). Two named carve-outs, both post-session and operator-triggered, so no write crosses the boundary while visitors hold the device: (a) live-doubt bank ingestion (item 12); (b) demo telemetry export — beacon events and error-map counters buffer LOCALLY on the venue instance during sessions (there is no network to send them over anyway) and export in the same operator step, always carrying the `demo` provenance flag. Resetting a rail restores the seeded state in one action between visitors.

**M3 — Make it resonate:**
8. **First-win opening (D3.3) — with the miss path designed, because for THIS audience the miss is the likely case.** The low-confidence rails open with a 3-item LA micro-diagnostic whose first item is genuinely easy and real; journey strip draws "you are here → GATE needs here"; one manipulable interactive early; rail ends on a previously-missed item now solvable (mastery-ending peak). Items real, win earned — honest-states law inside demo mode. **Miss choreography:** if the visitor misses item 1, the miss becomes the demo — the caption reframes ("that slip is exactly what Vidhya watches for — see what it does next"), the product responds visibly (full-step reveal, trap card for that error class), and the rail re-targets its ending peak to THAT item, so the session still closes on earned competence over the thing they just missed. A nervous student missing and then conquering is a stronger personalization proof than a clean win; the rail is designed for both, and both paths are QA-walked.
9. **Skeptic receipts rail (D3.2).** Principal card opens on the TeachingDashboard heatmap → syllabus-coverage taught-vs-mastered two bars → tap-through to attempts. Opening caption sets the frame: "Every number here is tappable. Try to catch it." Fixture coherence validator (item 5) is what makes this rail safe to offer.
10. **Split-screen personalization reveal (D3.1).** Demo-only view rendering the SAME LA lesson under two `EnrichmentContext`s (struggling vs confident fixture) side by side, differences highlighted (compressed vs full worked example, trap ordering, synthesized quick-check presence). Reached from both student rails and the principal rail — it is the one screen that serves both audiences identically.
11. **Demo captions (D3.4).** Thin overlay component, demo-mode only, caption scripts per rail in the same `config/demo-rails.json`, advancing on tap, dismissible. Captions narrate product behavior ("Vidhya noticed the sign-error slip — watch what it picks next"), never puffery. Zero footprint on student surfaces (component mounts only under the demo flag).
12. **Bring-your-own-doubt (D3.5).** One scripted rail point invites the visitor to pick any LA problem from their own material. Path: existing generation + verification, visible honest "verifying…" state with a time estimate. Guardrails: LA-scoped input; a pre-verified bank of ~20 likely textbook problems; on generation miss/timeout, the choreographed fallback offers the nearest pre-verified neighbor problem with the honest line ("that one needs longer than we have — here's its verified neighbor; I'll send yours after"). The miss is logged as an Observation (upstream-error posture: most valuable signal of the week). Input is typed/pasted problem text in v1 — photo/OCR intake is explicitly NOT in scope. **Bank round-trip, specified:** post-session, the operator ingests asked problems against the PRODUCTION instance (item-7 carve-out a: content tables, `demo_bank` tag); before the next demo, the refreshed bank re-exports to the local venue install as part of the pre-demo checklist — that round-trip is what "the bank compounds across demos" means. "I'll send yours after" = Giri sends the verified solution over the channel the visitor came from (WhatsApp), logged as an SSOT Touchpoint.

**Cross-cutting (all milestones):**
13. **SSOT integration.** Each student demo session runs under the observation call script and logs to People/Sessions/Observations same-day; sessions held this way count toward the 8-conversation gate. The principal logs as an E3-tagged People row; this plan is the recorded named decision that serves his demo without opening the E3 lane.

- Live-doubt bank format = the same verified-solution storage as regular content with a `demo_bank` tag; nothing bespoke.
- Persona set v1 is the four named; parent persona deferred until a parent is actually in a room.
- Reset between visitors is manual-triggered (one button), not time-based.

## Error map (zero silent failures; named)

| Error | Trigger | Caught by | Visitor/Giri sees | Tested |
|---|---|---|---|---|
| `InteractiveSpecUnrenderableError` | generated spec version/shape the renderer can't handle | render boundary per block | atom's static representation + counter; never a blank block | yes |
| `MathBoxAssetLoadError` | bundled 3D assets fail to load (device/memory) | interactive mount | `MathBoxLite` SVG fallback renders; counter | yes |
| `DemoRailConfigError` | demo-rails.json invalid (bad route, missing fixture, orphan caption) | build-time schema validation | build fails naming the card/field | yes |
| `FixtureCoherenceError` | aggregates don't reconcile to rows/attempts | fixture validator (CI + pre-demo smoke) | build/smoke fails with the first non-reconciling drill path | yes |
| `DemoWriteLeakError` | demo session attempts writing to real tables | storage-boundary assertion | hard fail in test; runtime guard drops write + alarms counter | yes |
| `CaptionTargetMissingError` | caption anchored to an element not on screen | caption overlay | caption skipped silently for the visitor, logged for the QA pass | yes |
| `LiveDoubtTimeoutError` | generation exceeds the stated estimate | live-doubt controller | choreographed fallback: nearest pre-verified neighbor + honest line | yes |
| `LiveDoubtVerificationFailedError` | solution generated but verification fails | verification gate | NEVER shown unverified; same fallback path; logged as top Observation | yes |
| `LiveDoubtOutOfScopeError` | problem outside LA scope | input scoping check | honest copy: "today's demo is Linear Algebra — send it to me and you'll get the verified solution after" | yes |
| `DemoResetIncompleteError` | reset leaves prior visitor's state | reset routine self-check | reset re-runs; button shows done only on verified clean state | yes |
| `FixtureSeedError` | a card's fixture fails to seed | seeder per card | card renders disabled with operator-visible reason; other cards unaffected | yes |
| `SplitScreenContextError` | one context's enrichment fails | split-screen renderer | single-pane render with labeled note; never a half-broken comparison | yes |
| `SamplePackLAGapError` | an LA exemplar missing atom types post-run | snapshot fixture (Aug-5 D8, extended) | CI set-diff names the concept and missing kinds | yes |

No catch-all handlers. Every counter above lands in the existing beacon/ledger paths — on the offline venue instance, via the local buffer + post-session export (item 7's carve-out b).

## Shadow paths (nil / empty / upstream error per new flow)

- Card deck: config empty → build fails (never an empty deck in front of visitors); one card's fixture fails seeding → `FixtureSeedError` path (disabled card, others unaffected).
- Split-screen: one context's enrichment fails → `SplitScreenContextError` path (labeled single-pane).
- Live-doubt: nil input (visitor declines) → rail continues, point skipped, nothing logged as a miss; empty/garbled typed problem text → out-of-scope copy path.
- Captions: script shorter than rail → rail simply continues uncaptioned (captions are garnish, never load-bearing); overlay crash → rail unaffected (component isolation).
- SSOT logging upstream failure (sheet unreachable at the venue) → paper-note fallback per the 24h rule; an unlogged session counts as not held, harsh on purpose (standing rule).

## Interaction edge cases

- Visitor abandons a rail mid-way → reset button restores seeded state; no partial fixture state leaks to the next visitor.
- Two visitors, one device, back to back → reset between; rails are stateless outside the seeded profile by construction.
- Two visitors, two devices, simultaneously (the vision's table scene) → per-device fixture instances (item 7); resets are device-scoped and cannot clobber the other walker.
- Low-confidence visitor misses the easy first item → the designed miss path (item 8): reframe caption, visible product response, peak re-targeted to that item. Never a dead moment, never a fake pass.
- Projector mirroring + low-end venue laptop → M1's offline smoke script runs on the actual demo device the day before; 3D path falls back per device capability, not resolution.
- Visitor taps fast through captions → captions are skippable by design; rail state never depends on a caption being read.
- Principal grabs the device during a student rail → nothing to hide: sample-data chips and receipts are the same surface for everyone.
- Double-tap on rail card → idempotent navigation guard (standing pattern).
- Demo device goes fully offline mid-rail → everything after M1 is local; live-doubt is the one network-dependent point and its timeout path covers venue-network death honestly.

## Observability

## Security

Demo mode adds no new authz surface: `/demo` ships enabled only on the demo deployment; if a public unlisted link is later wanted, that is the rung-1 tokenized-link work, not this plan. Fixture profiles contain no real student data. Demo writes are namespaced and boundary-guarded (`DemoWriteLeakError`). Live-doubt input (a visitor's problem) is processed by the existing generation consent posture and never stored against a real profile; problems joining the bank are content, not personal data. No new secrets; bundled MathBox removes a third-party CDN dependency (supply-chain surface shrinks).
