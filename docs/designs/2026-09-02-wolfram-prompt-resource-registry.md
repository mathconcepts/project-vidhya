## 1. Premise challenge

**Premise 1 — "10000x content improvement" is a literal, deliverable target.**
**Wrong, and the source document says so itself:** "The 10000x framing is
treated as an operational leverage hypothesis... learning-outcome gains
require controlled experiments." The uploaded materials never claim 10000x
quality improvement — they claim 10000x **reuse leverage** (one typed
resource serving many topics instead of one-off prompt text per topic),
which is a code-architecture claim, not a content-quality claim. This plan
implements the reuse architecture. It does not, and cannot, claim to have
made content 10000x better — no experiment framework in this pass measures
that, and none should be invented to satisfy a number from a hypothesis
document.

**Premise 2 — "regenerate/update the entire content of engineering
mathematics" is achievable in this session.**
**Wrong, evidenced, not a matter of effort.** No LLM provider key
(`GEMINI_API_KEY`/`ANTHROPIC_API_KEY`/`OPENAI_API_KEY`/etc.) is configured
in this environment — the same "known-unrun" constraint documented
throughout CLAUDE.md (v4.33.0, v4.43.0, the 2026-09-02 tone-directive PR
#150 landed on THIS branch two hours before this request). `orchestrator.ts`'s
`generateOne()` throws or falls through to a mock/stub the instant it needs
a live call. This is not a scope choice — it is a hard environment fact,
checkable and already checked (this session's boot banner and
`loadConfigFromEnv` resolution order both confirm no provider resolves).

**What "regenerate" becomes instead, matching the exact pattern this
codebase already used for the same constraint (P0-P7 pass, tone-directive
PR):** wire the registry into the LIVE generation path (`buildPrompt()`)
so every generation call from this point forward — the next time an
operator runs one, with a real key — uses it automatically. Build a
dry-run/audit CLI that reports, per atomic topic, which registered
resources/verifiers/modifiers apply and what's missing, using pure data
joins (no LLM call, runs today, produces a real artifact). Queue the actual
101-concept regeneration in TODOS.md as the next action once a provider key
exists — not silently dropped, not faked.

**This is presented as a Final Approval Gate item, not a mid-run
reinterpretation** — see §7.

**Premise 3 — the registry should be a new content-quality gate, parallel
to `content_gate_ledger`.**
**Worth correcting before building, not a hard "wrong."** The uploaded
registry's `release_gates` block conflates two different axes: is this
*prompt resource* safe to use (a code/prompt governance question — draft →
benchmarked → pilot → released → deprecated → blocked) vs. is this
*generated content item* safe to serve (already `content_gate_ledger`'s
job: scope/mathematics/assessment_contract/misconception_coverage/
provenance, fail-closed at serve + promote). Building a second content-item
gate would duplicate `content_gate_ledger` and violate DRY (P4). This plan
keeps them as two separate, already-precedented axes: resource governance
is new; content governance stays `content_gate_ledger`, untouched.

resource categories (`persona`, `research_function`, `teaching_function`,
`assessment_function`, `diagnosis_function`, `modifier`, `verifier`,
`renderer`, `governance` — 9 counting `governance`), 4 are fully covered by
existing code that just needs to be *registered* (verifier, teaching_
function via the atom-generation prompt blocks, assessment_function via
`GateDeterministicScorer`/`MarkingStrategy`, renderer via
`MarkdownAtomRenderer`/`gif-generator`/Manim), 3 are thin wrappers over
existing data (persona, modifier, governance via existing approval-state
precedents), and 2 are genuinely new slots with no implementation behind
them yet (research_function's claim-ledger extraction, diagnosis_function
beyond the existing bounded probe) — which is honest, not a shortfall: the
source document's own §15.6 custom-PDF pipeline (Vidhya's closest analog to
"research_function") is *itself* still an unimplemented interface by a
prior, already-reviewed decision.

## 3. Dream-state delta (0C)

```
CURRENT
  orchestrator.ts::buildPrompt() concatenates 4 hardcoded block-builder
  calls (painPointBlock, patternBlock, resonanceBlock, TONE_REGISTER_BLOCK).
  No versioning. No approval lifecycle. Disabling one block means editing
  code and shipping a deploy. No single place lists "every prompt-shaping

  A typed PromptResourceRegistry (src/content/prompt-registry/) with named,
  versioned resources across the 9 Wolfram-inspired categories. Existing
  block-builders register as resources (wrapped, not rewritten).
  buildPrompt() composes from the registry. A dry-run CLI
  (npm run content:registry-audit) reports per-topic resource coverage
  today, with zero LLM calls. wolfram_content_family joins onto the
  existing atomic-topic-spec crosswalk. content_gate_ledger is untouched.

12-MONTH IDEAL
  The registry generalizes past GATE-EM to every exam pack (BITSAT, NEET,
  civil services) without a second registry. An admin view lists resources
  with live approval-state transitions (mirrors ReviewQueuePanel's
  precedent — built ahead of pilot data per CLAUDE.md's W3.5 section). A
  real research_function claim-ledger exists once custom-PDF ingestion's
  extractor lands. Modifier promotion is data-driven off the existing
  lift-ledger/experiments system, giving the "10000x leverage" hypothesis
  an actual measurement path instead of a slogan.
```

(`src/content/prompt-registry`) and loses 4 direct calls to block-builder
functions (which move, not disappear, into `resources/teaching-blocks.ts`
and `resources/modifiers.ts` — same functions, new home, registered).

**Scaling:** the registry is in-process, module-scope (`Map<resource_id,

in-memory map — no new DB table, no new service, no new latency on the

**Security:** no new external input surface. Resource definitions are
authored in-repo (TypeScript objects), not user-submitted — same trust
boundary as `pedagogy-patterns.yml`, `template-families.yml`.
